# Как устроено внутри

## Путь пакета

```
устройство ──WireGuard(шифрование)──▶ ваш сервер ──▶ интернет
   (телефон, ноутбук)                  (wg0 + маршрутизация)
```

Между устройством и сервером трафик зашифрован ключами, которые сгенерированы на самом
сервере и не покидали его. Владелец кафейного Wi-Fi, гостиничного роутера или соседней
машины в сети видит только зашифрованный поток до вашего адреса.

Исходящий канал у узла появляется из пула после того, как в мастере введён ключ прокси-сервиса:
автоматика проверяет адреса и применяет лучший. Пока канала нет (сразу после установки), узел
выпускает трафик своим адресом — панель показывает это как «аварийный режим», для нового узла
это ожидаемо. Постоянный канал можно задать и вручную ещё до установки (`install/profiles.py`,
поле `upstream`) — тогда узел стартует сразу с ним.

## Компоненты

| Компонент | Роль |
|---|---|
| **WireGuard** (`wg0`) | шифрованный туннель, по профилю на устройство |
| **sing-box** | обработка исходящего трафика и маршрутизация |
| **vpn-boot-setup** | правила и маршруты, восстанавливаемые при каждой загрузке |
| **vpn-agent** | автоматика: проверки, самолечение, журнал |
| **vpn-panel** | веб-интерфейс на стандартной библиотеке Python |
| **сторож** | проверка связи каждые 2 минуты, запуск починки |
| **microsocks** | SOCKS5-прокси для приложений на `:1080` (по желанию); логин/пароль генерируются при установке |

## Почему без зависимостей

Панель написана на `http.server`, генератор QR-кодов — свой, ~400 строк на стандартной
библиотеке. Никакого PyPI, никаких CDN: страница запрещает внешние загрузки политикой
безопасности контента (`default-src 'none'`), поэтому весь интерфейс — это инлайновые стили
и скрипты плюс SVG.

Причина простая: каждая зависимость — это чужой код с доступом к узлу связи и ещё один канал
поставки для атаки. Для инструмента, чья задача — приватность, это неприемлемый размен.

## Устойчивость

* **Переживает перезагрузку.** Туннель поднимается на старте, маршруты и правила
  восстанавливаются юнитом `vpn-boot-setup`, панель стартует сама. Пока исходящий канал не
  выбран, тот же юнит сразу ставит прямой выход — устройства не ждут первой проверки сторожа.
  Проверяется тестом при установке.
* **Идемпотентность.** Повторный запуск установщика не задваивает правила и не теряет ключи:
  правила пишутся «проверь и добавь», а не «добавь ещё раз».
* **Самолечение по возрастающей.** Сторож видит обрыв → пробует подстроить настройки →
  переключается на запасной канал → в крайнем случае переводит клиентов на прямой выход,
  чтобы связь не молчала. Прямой выход переживает и перезагрузку, и повторную установку:
  агент восстанавливает его сразу, а не по расписанию повторов.
* **Откат.** Смена канала идёт по схеме «проверка → применение → повторная проверка», и при
  ухудшении конфигурация возвращается автоматически из кольца резервных копий.
* **Два режима выбора.** `AUTO(strategy)` разрешает стратегии выбирать канал. Успешное ручное
  «В бой» переводит узел в `MANUAL(uid, host)`: здоровый канал закреплён, стратегии и
  проактивная покупка резерва отключены, но проверки и продление продолжаются. Потеря сети
  сервера, единичный чих, сбой sing-box, RETUNE или отдельный отказ Telegram фиксацию не
  снимают. Только подтверждённый отказ самого прокси переводит узел в `AUTO(speed)`.
* **Последний выбор побеждает.** Панель и агент — разные процессы. Стратегия пишется в
  `config.json` атомарной заменой под межпроцессной блокировкой, а фоновый worker после
  получения общего lock заново читает последнюю цель и MANUAL. Поэтому быстрый второй клик
  или последующее «В бой» не могут быть перетёрты старым заданием.
* **Сначала выбор из пула, потом покупка.** Когда канал нужно сменить, узел перебирает уже
  купленные адреса (предпочитая надёжные страны выхода) и покупает новый **только если выбрать
  не из чего** — деньги не тратятся, пока в пуле есть живые запасные.
* **API сервисов — через собственный канал, если напрямую закрыто.** Узел ходит к сервисам
  аренды прокси напрямую; если соединение рвётся (у российских хостеров это случается с
  PROXY6), повторяет запрос через свой исходящий канал и запоминает рабочий путь. ProxyWing
  добавляет уже купленные datacenter/ISP-каналы через Bearer API v1; месячные покупки и
  продления намеренно выключены до отдельной денежной политики. Денежные
  операции повторяются только когда запрос заведомо не был доставлен — двойных покупок нет.

## Как выбирается канал

Все провайдеры попадают в один нормализованный пул. В формуле нет предпочтения PROXY6,
ProxyLine или ProxyWing: сначала отбрасываются строки без действующего API-ключа, `off/gone`,
cooldown и вечный чёрный список `ru/ua/by`, затем сравниваются замеры. Текущий канал получает
15 баллов устойчивости к бессмысленным переключениям.

Три стратегии меняют только вес страны и гейт будущей автопокупки:

| Стратегия | Вес страны | Порядок | Автопокупка |
|---|---:|---|---|
| Репутация | ×1 | страна первым ключом, затем замеры | рискованные страны запрещены |
| Баланс | ×0,5 | сумма репутации и замеров | всё вне чёрного списка |
| Скорость и отклик | ×0 | только живые замеры | всё вне чёрного списка; системный режим по умолчанию |

После клика кандидат проходит свежую пробу и ранжируется повторно: устаревший высокий score
сам по себе не является основанием для смены. Применение остаётся общей безопасной цепочкой
`probe → sing-box check → backup → apply → verify → rollback`.

## Что здесь называется обучением

Это осторожная адаптивная статистика, а не нейросеть. Узел агрегирует успешные/неуспешные
пробы, часы в бою и подтверждённые обрывы по паре «провайдер × паспортная страна». До 300
проб и 21 дня бонус строго нулевой; к 1000 пробам/60 дням β-сглаженная надёжность получает
полный вес, ограниченный диапазоном ±20. Этот бонус влияет только на порядок стран при
следующей покупке и никогда не отменяет чёрный список или денежные гейты. Текущий канал
всегда выбирается по свежему замеру.

Параметры из конфига нормализуются: битая строка, NaN, отрицательный порог или деление на
ноль не могут уронить панель либо денежное решение. Следующий этап модели — временное
затухание, доверительные интервалы и раздельная статистика конкретного IP — описан в
[плане надёжности](reliability-plan.md).

## Данные и файлы на сервере

| Путь | Что там |
|---|---|
| `/etc/wireguard/wg0.conf` | конфигурация туннеля (`0600`) |
| `/etc/wireguard/clients/` | профили устройств с приватными ключами (`0600`) |
| `/etc/vpn-panel/config.json` | настройки узла и ограничения (`0644`; стратегия и автообновление меняются точечно из панели, лимиты денег — только по SSH) |
| `/etc/vpn-panel/secrets.json` | пароль-хеш, второй фактор, ключи сервисов (`0600`) |
| `/var/lib/vpn-panel/state.db` | база: журнал действий, состояние, история |
| `/opt/vpn-panel/` | код агента и панели |
| `/etc/microsocks.env` | логин и пароль SOCKS5-прокси, сгенерированные при установке (`0600`) |

## Безопасность панели

* пароль хранится хешем (scrypt), второй фактор — TOTP, плюс 10 одноразовых резервных кодов;
* 5 неудачных попыток входа → временный бан адреса, дальше пауза растёт;
* сессии в cookie `httpOnly` + `Secure` + `SameSite=Strict`, CSRF-токен на все действия;
* заголовки `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`;
* TLS — самоподписанный сертификат на 10 лет, сверяется по отпечатку при первом входе; на
  рабочем узле панель **работает только по HTTPS** — сертификат выпускается до её старта, и
  без него панель не поднимается (пароль и второй фактор никогда не идут открытым текстом);
* опасные настройки (лимиты расходов) недоступны из браузера в принципе.

## Тесты

```bash
cd agent && python -m unittest discover -s tests
```

568 тестов покрывают скоринг и порядок выбора каналов (включая все стратегии, AUTO/MANUAL,
гонки быстрых переключений и независимость от провайдера), покупку только когда в пуле
выбрать нечего, политику расходов с её ограничениями, автопродление, разбор
ответов внешних сервисов, состояния автоматики (включая восстановление прямого выхода после
перезагрузки), правку загрузочного скрипта при смене канала (в том числе новый формат с прямым
выходом при пустом канале), выбор транспорта к API сервисов (прямой / через свой канал, правила
для денежных операций), требование HTTPS для панели и защиту от двойных операций.
