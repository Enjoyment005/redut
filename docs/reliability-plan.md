# План развития архитектуры и надёжности Redut

Дата аудита: 2026-08-22. Базовая версия после исправлений: 1.11.0.

## Цель

Redut должен вести себя как автомат состояний с проверяемыми инвариантами, а не как набор
кнопок и cron-команд. Любое действие обязано быть:

1. объяснимым — в журнале видно, почему принято решение;
2. идемпотентным — повтор не создаёт вторую покупку, ротацию или полусостояние;
3. сходящимся — после гонки процессов побеждает последнее намерение владельца;
4. обратимым — изменение канала имеет проверку и автоматический откат;
5. безопасным по умолчанию — неизвестность не считается отказом и не тратит деньги.

Неприкосновенные правила: чёрный список `ru/ua/by`, денежные гейты, общий lock изменения
канала, проверка нового egress после применения и сохранение связи через прямой аварийный
выход.

## Проверенная модель выбора

### Три стратегии

| Стратегия | Вес страны | Первичный ключ | Автопокупка | Назначение |
|---|---:|---|---|---|
| `reputation` | 1,0 | репутация страны | рискованные страны закрыты | меньше капч и антифрода |
| `balanced` | 0,5 | общая сумма | всё вне ЧС | компромисс |
| `speed` | 0 | живые замеры | всё вне ЧС | системный default и аварийный fallback |

Все провайдеры нормализуются в один пул. Название провайдера не входит в score и не является
tie-break: ProxyWing, ProxyLine и PROXY6 конкурируют одинаково. Строка исключается только при
отсутствии активного адаптера/ключа, роли `off/gone`, cooldown или запрещённой стране.

Текущий канал получает +15 баллов stickiness. Непроверенный кандидат получает стартовые
100 баллов и шанс на живую пробу. После клика лучший кандидат пробуется заново и повторно
ранжируется: старый score не является достаточным основанием для переключения.

### Режимы AUTO/MANUAL

| Событие | Было MANUAL | Результат |
|---|---:|---|
| канал здоров | да | `MANUAL`, только наблюдение |
| сеть самого сервера недоступна | да | `MANUAL` сохраняется, `FROZEN_NET` |
| не отвечает только Telegram | да | `MANUAL` сохраняется, деградация отдельно |
| сломан sing-box/tun0 | да | self-heal, `MANUAL` сохраняется |
| текущий IP жив через другой протокол | да | RETUNE, `MANUAL` сохраняется |
| первая неудачная проверка | да | SUSPECT + повтор, `MANUAL` сохраняется |
| повтор прошёл | да | flap, ничего не меняется |
| подтверждён отказ самого прокси | да | `AUTO(speed)` до ранжирования замены |
| владелец выбрал стратегию | да | `AUTO(выбранная)` немедленно |
| владелец снова нажал «В бой» | любое | новый `MANUAL(uid, host)` |
| удалён API-ключ провайдера ручного канала | да | здоровый канал остаётся до реального отказа |
| успешный ручной rollback | любое | восстановленный канал становится `MANUAL` |

Ручной режим блокирует проактивную покупку N+1, но не блокирует refresh пула, безопасные пробы
уже купленных каналов и автопродление текущего IP.

### Лестница отказа

`network → egress → sing-box → RETUNE → повтор verify → ROTATING → REPLENISH → EMERGENCY`.

MANUAL снимается только между подтверждением proxy fault и ROTATING. Это место должно
оставаться единственной автоматической точкой перехода `MANUAL → AUTO(speed)`.

## Что исправлено в 1.11.0

- Добавлено устойчивое состояние `AUTO/MANUAL` в SQLite; поля режима меняются одной
  транзакцией.
- `speed` стал единым default в коде, чистой установке и deploy-профилях.
- Ручное «В бой» закрепляет канал только после успешных probe/apply/verify.
- Явный выбор любой стратегии снимает MANUAL.
- Подтверждённый отказ сохраняет `speed` атомарно; ошибка записи файла не блокирует failover,
  а оставляет pending override для следующего цикла.
- Запись `config.json` вынесена в общий writer: межпроцессный flock, уникальный temp, fsync,
  `os.replace`, сохранение соседних полей.
- Исправлено расхождение score и порядка: +15 текущего канала теперь участвуют и в UI-preview,
  и в фактическом выборе.
- Устранена гонка фиксированного systemd-unit. Каждый worker имеет уникальное имя, ждёт общий
  agent-lock, читает последнюю стратегию после ожидания и не может перебить появившийся MANUAL.
- Перед применением кандидат повторно ранжируется после свежей пробы.
- Параметры адаптивной статистики нормализуются; NaN, отрицательные пороги и нулевые делители
  не роняют денежное решение.
- Матрица покрыта 568 публичными тестами; живой canary-приёмке подлежит узел `vadim`.

## Аудит встроенного обучения

### Что работает сейчас

Это не ML-модель, а безопасный статистический бонус к будущей покупке.

Ключ: `provider × passport_country`.

Сигналы:

- число успешных и неуспешных проб;
- подтверждённые обрывы боевого канала;
- накопленное время пары в бою;
- возраст наблюдений.

До 300 проб и 21 дня результат строго равен нулю. Полный вес достигается к 1000 пробам и
60 дням. Надёжность сглаживается Beta prior, штраф за обрывы ограничен, общий бонус зажат
в диапазоне ±20. Бонус влияет только на сортировку стран при покупке; live-канал выбирается
по свежим измерениям.

На `vadim` на момент аудита накоплено около четырёх дней данных. Все пары незрелые, поэтому
их бонус `0.0` — это правильное поведение защиты от ранних выводов, а не поломка.

### Сильные стороны

- малая выборка не влияет на деньги;
- неизвестность нейтральна;
- чёрный список и auto-gate невозможно обойти бонусом;
- техническая история не подменяет свежую пробу;
- формула детерминирована и тестируема.

### Ограничения

1. История накапливается навсегда: старый плохой месяц не забывается после улучшения сервиса.
2. Нет окон 7/30/90 дней и обнаружения дрейфа.
3. Нет доверительного интервала; показывается точечный процент.
4. Агрегация слишком крупная: конкретный IP, тип `datacenter/ISP`, ASN и тариф смешиваются.
5. Паспортная и фактическая страна разделены только частично; ошибочная продажная метка может
   скрыть систематический geo-mismatch.
6. Частота фоновых проб влияет на скорость созревания пары; большой пул учится быстрее.
7. Общая проблема сети сервера может записать серию провалов сразу нескольким парам.
8. Обрыв учитывается не во всех исходах: уход в EMERGENCY без успешной замены способен
   недосчитать battle drop.
9. Нет контролируемого exploration: система почти не получает новые данные о проигрывающих
   вариантах.
10. Нет offline replay: изменение формулы нельзя заранее прогнать по историческому журналу.
11. Модель оценивает техническую доступность, но не знает о капчах, оплатах и бизнес-результате.
12. Обучение влияет только на покупку, а не объясняет оператору выбор live-канала.

Вердикт: текущая реализация безопасна и корректна как «статистика v1», но пока слишком
медленная и грубая, чтобы называться полноценным самообучением.

## Приоритетный roadmap

### P0 — целостность управляющего контура

#### 1. Журнал операций (saga)

Добавить таблицу `operation`:

- `id`, `kind`, `requested_by`, `desired_state`;
- фазы `planned/probing/staged/applied/verifying/committed/rolled_back/failed`;
- `from_uid/to_uid`, checksum конфигов, timestamps, error;
- уникальный idempotency key.

На старте агент восстанавливает незавершённую операцию по фактическому sing-box, маршрутам и
backup-кольцу. SQLite, `config.json`, sing-box и iptables нельзя сделать одной транзакцией,
поэтому переход должен быть явной восстанавливаемой saga.

Критерий: kill -9 в любой фазе не оставляет неизвестное состояние и не требует ручной
догадки.

#### 2. Постоянный desired-state reconciler

Стратегия уже сходится при быстрых кликах, но transient worker может исчезнуть при reboot.
Хранить `desired_selection_revision` и `applied_selection_revision` в БД. На старте панели,
каждом pool-refresh и безопасном heartbeat агент проверяет расхождение и доводит канал.

Критерий: reboot сразу после POST стратегии всё равно приводит к последнему выбору без
повторного клика.

#### 3. Версионированная схема конфигурации

- `config_schema_version`;
- строгая нормализация всех чисел, enum, путей, сетей и денежных лимитов;
- миграции `N → N+1` с backup и dry-run;
- отказ только опасного действия, а не запуска всей панели;
- диагностический endpoint «эффективный конфиг + источник default», без секретов.

Критерий: fuzz повреждённых полей не приводит к покупке, удалению, traceback или silent
fallback без события.

#### 4. SQLite под несколькими процессами

Оценить WAL + `synchronous=FULL`, единый transaction helper, retry с jitter и явные классы
ошибок `busy/corrupt/disk-full`. Все многополевые переходы писать транзакцией, события —
в той же транзакции, что и состояние.

Критерий: параллельные panel/cron/watchdog тесты не дают `database is locked`, потерянных
событий и полусостояний.

### P1 — здоровье и выбор

#### 5. Freshness как часть score

Для каждого сигнала хранить возраст. После TTL score плавно теряет доверие, а не остаётся
вечным. Перед проактивной сменой обязательно обновлять top-кандидата; текущий измерять без
разрыва соединения.

Критерий: прокси с отличным score недельной давности не обгоняет свежий стабильный канал.

#### 6. Гистерезис и цена переключения

Сделать параметры `switch_margin`, `min_hold_time`, `max_latency_regression`.
Stickiness +15 оставить базой, но объяснять решение численно: «кандидат лучше на 22, порог 15».

Критерий: при шуме ±10% нет флаппинга; критический отказ обходит hold-time.

#### 7. Кворум сигналов

Разделить причины: server network, DNS, Telegram, HTTP, SOCKS, provider API, geo. Решение о
proxy fault принимать по кворуму независимых проверок и общей временной шкале, сохраняя
быстрый путь для явного TCP refusal.

Критерий: outage одного внешнего сайта не меняет IP; реальный отказ укладывается в SLO.

#### 8. Контракты провайдеров

Единый тип capability и ошибок: auth/rate-limit/network/not-found/expired. Контрактные тесты
на сохранённых обезличенных ответах API, circuit breaker и `Retry-After`. Никакой провайдер
не получает скрытого приоритета; новый адаптер обязан пройти общий conformance suite.

### P1 — обучение v2

#### 9. Временное затухание

Вместо вечных counters использовать дневные buckets и EWMA/окна 7, 30 и 90 дней. Хранить
старый агрегат для миграции и аудита.

#### 10. Иерархическая статистика

Уровни:

`global → provider → provider/family → provider/country → uid/ASN`.

Малая группа наследует prior родителя, зрелая получает собственный вес. Техническую
надёжность, geo-честность, latency и battle drops считать отдельными признаками.

#### 11. Неопределённость и exploration

Использовать Beta posterior/Wilson lower bound. Показывать sample size и интервал. Допускать
ограниченное exploration только среди уже купленных резервов; автоматические покупки ради
эксперимента запрещены без отдельного бюджета владельца.

#### 12. Offline replay и shadow mode

Новая формула сначала 30 дней считает рекомендации в `shadow_decision`, не меняя канал и не
тратя деньги. Replay исторического `probe_log/event/money` сравнивает:

- число лишних переключений;
- среднюю/95p latency;
- долю времени без рабочего proxy;
- расходы;
- долю ошибок выбора по факту следующей пробы.

Включение влияния — canary на `vadim`, затем один узел, затем остальные.

### P1 — наблюдаемость

#### 13. Объяснение каждого решения

Структурированное событие должно содержать strategy, mode, score breakdown, freshness,
margin, список исключённых кандидатов и причину. В панели — одна короткая строка и раскрываемая
диагностика.

#### 14. Метрики и SLO

Минимальный локальный набор:

- availability egress и Telegram;
- MTTR подтверждённого proxy fault;
- switch success/rollback rate;
- switches per day и false-switch rate;
- время MANUAL, причины выхода;
- stale-score decisions;
- provider API errors/rate limits;
- spend/day и denied spend;
- learning coverage/maturity/drift.

### P2 — масштабирование

- Общий бюджет нескольких серверов: локальные суточные лимиты сейчас не глобальны.
- Координатор аренды, чтобы два узла не купили одновременно.
- Репликация только агрегированных метрик; приватные ключи и клиентские профили не выносить.
- Разделить control plane и data plane лишь после появления минимум трёх постоянно работающих
  узлов: раньше это добавит больше отказов, чем устранит.
- Поддержка нескольких одновременных upstream на клиента/класс трафика — отдельная функция,
  не часть обычной стратегии одного канала.

## Матрица обязательных испытаний

### Состояния

- AUTO × три стратегии × OK/SUSPECT/ROTATING/EMERGENCY/FROZEN_NET;
- MANUAL × все те же состояния;
- reboot и kill -9 на каждой фазе apply/rollback;
- ручной клик во время strategy worker, rotate, update и provider refresh;
- удаление ключа текущего/резервного провайдера в AUTO и MANUAL;
- исчезновение текущей строки из пула при живом sing-box;
- read-only/disk-full/corrupt `config.json` и `state.db`.

### Сеть

- умер серверный WAN;
- умер только proxy;
- не отвечает только Telegram;
- жив HTTP, мёртв SOCKS и наоборот;
- DNS outage;
- высокий packet loss и latency jitter;
- provider API 401/429/500/timeout/битый JSON;
- IPv4/IPv6 и расхождение geo-баз.

### Деньги

- timeout до отправки и после принятия buy;
- параллельная покупка;
- суточный лимит на нескольких узлах;
- неверная валюта/цена/остаток;
- покупка прошла, post-probe не прошёл;
- повтор после reboot не списывает второй раз.

## Целевые SLO

| Метрика | Цель |
|---|---:|
| ложная смена здорового ручного канала | 0 |
| потеря последнего выбора стратегии | 0 |
| двойная покупка/продление | 0 |
| восстановление после подтверждённого proxy fault, если резерв жив | p95 ≤ 3 мин |
| успешный apply без rollback | ≥ 99% для кандидатов после пробы |
| необъяснённое решение без event | 0 |
| повреждение live-конфига при disk/process fault | 0 |
| автоматические смены при Telegram-only outage | 0 |
| флаппинг | ≤ 1 лишней смены на узел за 30 дней |

## Порядок внедрения

1. Выпустить 1.11.0: AUTO/MANUAL, default speed, atomic config, convergent worker.
2. Canary на `vadim`: все стратегии, ручной healthy-cycle, безопасный выход в AUTO,
   сервисы, Telegram, reboot.
3. Добавить operation saga и desired revision; провести kill-point chaos suite.
4. Включить WAL/transaction helper после отдельного теста миграции и rollback.
5. Собрать 30–60 дней baseline текущего обучения.
6. Реализовать learning v2 в shadow mode и offline replay.
7. Разрешить v2 влиять на покупку только после canary и сравнения SLO.
8. Рассматривать общий control plane лишь после стабилизации одиночного узла.

## Definition of Done для каждого следующего релиза

- новая ошибка закреплена тестом или автоматическим repair;
- main и публичный пакет проходят полный набор;
- чистая установка и повторная установка проверены;
- миграция старой БД/конфига и rollback проверены;
- canary сохраняет клиентов, секреты и текущий канал;
- healthcheck, Telegram, панель и обновление зелёные;
- документация описывает фактическое, а не желаемое поведение;
- версия, commit, tag и GitHub release совпадают.
